## BOOK-STRIP-LOCK-EPERM-20261108: watcher cycle killed by a transient lock-write PermissionError (CURED)

- Severity: cycle-fatal, self-healing by cadence (one 5-minute
  cycle lost, no republication that cycle; the book strip itself
  stayed at its last successful publish).
- File: site/watch_book_strip.py, acquire_lock().
- What broke: the Sun 2026-11-08 09:48:08 ET run of cron
  midna-book-strip-watch (run e80c054d-35a5-4d3e-8f09-976655d6acbd)
  died with PermissionError: [Errno 1] Operation not permitted at
  LOCK.write_text inside acquire_lock(), exit 1, and was reported
  FAILED. Root cause, proven from the filesystem state and the
  run record: the lock path (~/workspace/research_notes/
  midna-book-strip-20261104/watcher.lock, directory drwxrws---
  root:nogroup on the local /home/hatch mount) was not stale,
  not held, and not mis-permissioned: the 09:43 cycle finished in
  16s and the 09:53 cycle succeeded, the lock file was absent
  between cycles, and every other cycle in the 06:33 to 14:48 ET
  window (100 runs read) succeeded on the identical create/write/
  release path. The EPERM was a transient host sandbox permission
  wall on that single lock write (the class the 2026-11-08 daily
  log recorded as hit elsewhere the same day). The defect at the
  source was in the code: acquire_lock() let an OSError from the
  lock write escape and kill the whole cycle, unlike every other
  failure mode in the watcher (generator and publish failures are
  logged and retried next cycle). A lock-acquisition failure is
  benign by the watcher's own design: hashes are recorded only
  after a successful publish, so a skipped cycle retries the same
  change 5 minutes later.
- Fix: acquire_lock() now catches OSError from LOCK.write_text,
  records a LOCK-UNAVAILABLE line in the republication log when
  it is writable, and returns False, degrading to the existing
  respected-lock outcome (main prints LOCKED, exit 0, no
  publish). No other watcher behavior changed; the cron body was
  not touched.
- Regression blocker: site/test_book_strip_lock_20261108.py
  (standalone, test_*.py style): a lock path whose write_text
  raises PermissionError(1) must make acquire_lock() return False
  and main() exit 0 with the LOCKED line; a fresh lock is
  respected untouched; a stale lock is taken over; a normal
  acquire/release cycle writes and removes the pid file.
  Fail direction proven 2026-11-08: on the pre-cure code the
  blocker FAILed with exactly the incident error escaping both
  acquire_lock() and main() (2 failures); after the cure it
  PASSes (0 failures). Proof by effect on the live paths: a
  watcher cycle run after the cure printed NO-CHANGE with exit 0
  (lock acquired and released; no lock file left behind).
- Note on the neighbouring blocker: site/test_book_strip_
  20261104.py was re-run after this cure; its watcher-trigger
