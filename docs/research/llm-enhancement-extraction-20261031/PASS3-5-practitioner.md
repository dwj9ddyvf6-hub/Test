## 1. simonw/llm: fragments, logs, templates, plugins (proper inspection)

Source paths read in full or in load-bearing part: `README.md`, `docs/fragments.md`, `docs/templates.md`, `docs/logging.md`, `docs/plugins/plugin-hooks.md`, `docs/plugins/directory.md`, `docs/embeddings/index.md`.

**Fragments (the ecosystem's real memory mechanism).** Verbatim: "LLM prompts can optionally be composed out of **fragments** - reusable pieces of text that are logged just once to the database and can then be attached to multiple prompts." A fragment is addressed by URL, file path, alias, stdin, or "Hash IDs of stored fragments, where the ID is the SHA256 hash of the fragment content"; fragments can also be produced by plugins via a `plugin-name:argument` prefix syntax. The plugin directory shows the pattern at work: `llm-fragments-github` loads a whole repo (`-f github:simonw/files-to-prompt`), `llm-fragments-pdf` converts PDFs to Markdown, `llm-hacker-news` imports a thread, `llm-video-frames` turns video into JPEG frames for vision models. So context assembly is content-addressed, deduplicated by hash, logged once, and composable across prompts, with an open loader namespace.
**Verdict: ADOPT-IDEA (new find).** Content-addressed reusable context pieces are not in the adopted set: passes 1 and 2 covered memory of facts and procedures, not a hash-addressed fragment layer for prompt context (research corpora, teardown bundles, chart packs) where the same large context is attached to many runs and should be stored and cited once, by hash. Small build on top of existing file storage; the hash ID doubles as the provenance stamp pass 2's rationale-memory discipline wants.

**Logging as the default memory substrate.** `llm` logs every prompt and response to a SQLite `logs.db` by default, with a per-item `--no-log` opt-out and a global on/off; each row carries an id, model, prompt, system, response, `conversation_id`, `duration_ms`, and `datetime_utc`, and `llm logs` re-renders the most recent items as Markdown or JSON with response-only and fenced-code extraction modes. **Verdict: ALREADY-HAVE** (transcript store plus nightly synthesis is the same shape, richer), with one REFERENCE detail worth copying into any future local CLI tooling: logging on by default with an explicit per-call opt-out, rather than logging as an opt-in, is what makes the corpus complete enough to mine later.

**Templates.** A template "can combine a prompt, system prompt, model, default model options, schema, and fragments into a single reusable unit", saved as YAML in a dedicated directory, with `$input` placement, `$$` escaping, baked-in tools/functions and JSON schema. **Verdict: ALREADY-HAVE** (SKILL.md playbooks are this, with gates and evidence rules the YAML template lacks).

**Plugin system.** Pluggy hooks, imitating Datasette: `register_models`, `register_embedding_models`, `register_commands`, `register_tools`, plus fragment/template loaders (since 0.24). Plugins are ordinary Python packages discovered by entry point. **Verdict: REFERENCE.** The transferable point is the narrowness: four registration hooks cover models, embeddings, commands, and tools, and a fifth covers context loading. No memory plugin as such exists in the directory (see looked-and-empty ledger): in this ecosystem memory is fragments plus the log database, not a store.

**simonw/tools** (1,924 stars): dozens of single-file HTML tools, "almost entirely generated using LLMs", each a self-contained page. **Verdict: REFERENCE / ALREADY-HAVE** (generated artifacts already realise this; the discipline of one file, no build step, no backend is a good default for small tools and is already this stack's artifact habit).

## 2. anthropics/skills and the skill-creator (proper inspection)

Source paths: repo `README.md`, `template/SKILL.md`, `skills/skill-creator/SKILL.md` (read in load-bearing part).

**The official spec is radically minimal.** The template's frontmatter has exactly two fields, `name` and `description`, and the README states: "The frontmatter requires only two fields." A skill is a folder with a `SKILL.md` plus optional scripts, references, and assets, distributed here as a Claude Code plugin marketplace (`/plugin marketplace add anthropics/skills`). **Confidence note (no verdict change):** this is the vendor's own floor, and it cuts both ways for the adopted disciplines. It confirms pass 1's description-hygiene finding from the opposite direction (the `description` is the entire triggering surface, which is why Superpowers' triggers-only rule and everything-skills' negative boundary matter), and it warns against over-reading everything-skills' rich frontmatter schema (pass 1, ADOPT-IDEA schema only) as a standard: the canonical ecosystem runs on two fields, so any extra local fields are local governance, not portability. Local skills that may ever be shared should keep name and description spec-clean and put extra metadata where it does not break the two-field contract.

**skill-creator: the vendor's own eval loop.** Verbatim process summary from the file: draft the skill, "Create a few test prompts and run claude-with-access-to-the-skill on them", evaluate "both qualitatively and quantitatively", draft quantitative evals while runs happen, rewrite from feedback, "Repeat until you're satisfied", then expand the test set; afterwards a separate description improver "optimize[s] the triggering of the skill". It also prescribes capturing intent from an existing conversation first (tools used, sequence, corrections, input/output formats) before writing anything.
**Confidence verdict: CONFIRMS adopted discipline 6/7 (TDD-for-skills and the skill adoption/eval gate), strengthened.** Pass 1 derived the eval-before-adopt discipline from Superpowers, promptfoo, and a third-party scanner; the platform vendor's own shipped skill independently prescribes the same loop, including the two parts pass 2 had to excavate from Superpowers (test the skill by running it, and treat description triggering accuracy as a separately optimisable, measurable quantity). No direction change; the evidence base for the discipline is now vendor plus two independent community sources. One divergence worth noting: the vendor loop is human-in-the-loop and satisfaction-terminated ("until you're satisfied"), with no pass^k-style reliability threshold; the local gate-wired version remains stricter, correctly for high-stakes playbooks.

## 5. Shubhamsaboo/awesome-llm-apps, mined for patterns (proper inspection of the pattern-bearing entries)

Repo README parsed in full (all template categories). Pattern-bearing entries read individually:

**Self-Improving Agent Skills** (`agent_skills/self-improving-agent-skills/README.md`, full). A three-agent loop over a skill: an **Executor** that runs the skill against generated test scenarios and scores outputs against binary yes/no criteria (it also generates the scenarios, 3-4, and criteria, 4-6, which the human may edit before the loop starts), an **Analyst** that "diagnoses failure patterns and picks a strategy (`add_example`, `add_constraint`, `restructure`, or `add_edge_case`)" with a Pydantic `output_schema`, and a **Mutator** that "applies ONE surgical fix to the skill prompt". Loop rule, verbatim: "Changes are kept if the score improves, reverted if not. Repeats until the target pass rate is reached or max rounds hit."
**Verdict: ADOPT-IDEA (new find, as a decomposition). Confidence verdict: CONFIRMS the fainir self-improvement slivers and Superpowers' micro-testing.** Pass 2 adopted the keep-if-better/revert-if-worse loop from a prompt document with no deployment; here is the same loop as shipped app code structure with three separable roles and a named four-value mutation-strategy enum. The decomposition (executor / analyst / mutator as separate passes, one mutation per round, binary criteria) is the concrete form a native skill-improvement lane should take, and the mutation-strategy enum is a ready-made vocabulary for the change log of any such lane.

**Scope Creep Detector** (`agent_skills/scope-creep-detector/README.md`, full). A deterministic, standard-library-only, no-network script that checks a diff "against a one-line intent", flagging "unrelated paths, new dependencies, public API renames, config or CI edits, oversized hunks, formatting-only files, and subsystem spread", emitting a local JSON report "for keep, split, or justify decisions".
**Verdict: ADOPT-IDEA (new find, high value for this stack).** InfinityBlade mandates minimum sufficient change and SCOPE-first, and pass 2's bounded-loops transfer protected the gate from the worker; nothing adopted so far mechanically audits a finished diff against its stated intent. This is that audit, in the cheapest possible form (deterministic, stdlib, read-only), and it maps directly onto reviewing delegated work: intent line in the brief, scope report attached to the handback, flagged hunks require keep/split/justify. It composes with, and does not duplicate, the false-green audit (that checks tests; this checks scope).

**Trust-Gated Multi-Agent Research Team** (`advanced_ai_agents/multi_agent_apps/trust_gated_agent_team/README.md`, full). Agents scored 0-100 and tiered, a threshold gate before participation, and a SHA-256 hash-chained audit trail where each entry's hash covers "sequence + timestamp + agent + action + input_hash + output_hash + trust_score + prev_hash", exported as independently verifiable JSON.
**Verdict: ALREADY-HAVE.** Pass 2's eval-capsule adoption (hash-chained NDJSON, effect classes) is this pattern in stronger form; the demo's trust scores are static fixtures, not measured, so nothing transfers except confirmation that hash-chaining is the ecosystem's convergent answer.

**The rest of the collection, pattern-mined:** the "LLM Apps with Memory" tutorials (6 entries) are all single-store wrappers (session chat history, Mem0-style personalised memory, shared conversation memory across models); pass 1's Mem0 verdict covers the mechanism and none adds a schema. The two "Always-on Agents" are scheduled scouts producing ranked briefs (Hacker News digest, dependency Release Radar) with no intervention-cost or gating concept; ALREADY-HAVE via cron lanes, and a small confirming data point for proactivity discipline 5: the practitioner ecosystem's always-on pattern is exactly the ungated generator pass 2 warned about. "AI Self-Evolving Agent" delegates self-modification to an external framework (EvoAgentX) with no keep/revert evidence rule visible at README level; SKIP as a pattern source (the Section 5 loop above is the same idea with the evidence rule intact). Agent Skills category header claims "Every skill ships real code and passes a security + eval CI gate"; the claim is stated, not evidenced in the files read, so it is recorded as a claim, not as corroboration.

## 6. LangMem: memory types and the prompt optimizer (proper inspection)

Source paths: `README.md` (full), `docs/docs/concepts/conceptual_guide.md` (load-bearing sections).

The conceptual guide's memory-type table is the cleanest framework statement of the taxonomy: **Semantic** (facts and knowledge; represented as a Profile with a strict schema, or a Collection to be searched), **Episodic** (past experiences; "Few-shot examples; Summaries of past conversations"), **Procedural** (system behaviour; "Prompt rules or Collection"). Two mechanisms pass 1 and 2 did not extract from any source:

1. **Episodic memory as a few-shot example collection.** Verbatim: episodic memory "captures the full context of an interaction - the situation, the thought process that led to success, and why that approach worked", stored to be retrieved as learning examples for future behaviour, distinct from semantic facts. The adopted set stores episodes as daily logs and lessons, but does not retrieve successful past interactions *as few-shot exemplars* at task time. **Verdict: ADOPT-IDEA (new find).** A small, file-native build: a curated exemplar collection per recurring task class (situation, approach, why it worked), retrieved alongside memory search. It is the retrieval-side twin of instincts (which store the distilled rule; this stores the worked example the rule came from).
2. **Procedural memory as a bounded prompt optimizer.** The guide's procedural path is a metaprompt optimizer over the agent's own instructions, configured in its example with `max_reflection_steps: 3`, driven by conversation feedback; LangMem splits memory work into hot-path tools (agent-managed during conversation: `create_manage_memory_tool`, `create_search_memory_tool` over a namespaced store) and a background memory manager that "extracts, consolidates, and updates" knowledge.
**Confidence verdict: CONFIRMS disciplines 2 and 6 in direction, WARNS on one boundary.** A major framework independently ships procedural memory as a first-class type, corroborating the instincts adoption; but its procedural update is automatic prompt rewriting from conversations, where the adopted local design keeps promotion human-gated. The warning is concrete: LangMem's own guide gives the optimizer a reflection-step cap but no evidence gate of the keep-if-better form in Section 5. If a native prompt optimizer is ever built, Section 5's scored keep/revert rule, not LangMem's reflection loop, is the safer template. Also recorded: the guide states recall relevance should combine similarity with importance and with strength as "a function of how recently/frequently it was used", a third independent statement of the composite-scoring shape (see Section 7).

## 7. CrewAI unified Memory, as shipped code (proper inspection)

Source path: `lib/crewai/src/crewai/memory/unified_memory.py` (1,050+ lines; class definition and defaults read verbatim). This is the current shipped design, replacing the older short-term/long-term/entity/user four-store split in current docs. The `Memory` class "Uses LLM to infer scope, categories, importance on save" and ships these defaults, verbatim from the field definitions:

- Composite recall score weights: `recency_weight` 0.3, `semantic_weight` 0.5, `importance_weight` 0.2; `recency_half_life_days` 30 ("Recency score halves every N days").
- `consolidation_threshold` 0.85 ("Similarity above which consolidation is triggered on save"), `consolidation_limit` 5.
- `default_importance` 0.5; analysis LLM default `gpt-5.4-mini`; storage default LanceDB.
- **Adaptive recall depth:** `confidence_threshold_high` 0.8 ("Recall confidence above which results are returned directly"), `confidence_threshold_low` 0.5 ("below which deeper exploration is triggered"), `complex_query_threshold` 0.7, `exploration_budget` 1 ("Number of LLM-driven exploration rounds during deep recall"), `query_analysis_threshold` 200 ("Queries shorter than this skip LLM analysis during deep recall").
- A `read_only` mode in which `remember()` stores nothing, `update()` is a no-op, and `recall()` does not refresh access times; hierarchical scopes with `root_scope` prefixing, `scope()`/`slice()` views, and categories inferred per record.

**Verdict: ADOPT-IDEA (one new mechanism), plus a confidence verdict.** The new mechanism is **confidence-gated adaptive recall depth**: a cheap first recall whose confidence decides, against two named thresholds, whether to return, or to spend a bounded number (default exactly 1) of LLM-driven exploration rounds, with short queries exempted from analysis entirely. Pass 2's SLM adoption gave honest recall *tiers* (a labelling discipline) and Mem0 gave a fusion *formula*; neither gave an escalation policy for what to do when the first recall is weak. This is that policy, with production defaults. **Confidence verdict: CONFIRMS discipline 7 (memory discipline at numeric level) and slightly rebases its numbers.** CrewAI is a second, independent, shipped implementation of composite scoring, and its weights are simpler than Mem0's published fusion (flat 0.5/0.3/0.2 with a 30-day half-life versus semantic-gated additive scoring with sigmoid BM25). Two frameworks converging on composite scoring confirms the shape; the divergence in complexity is evidence that the simple weighted form is the production default and Mem0's formula is the sophisticated end. A native build should start from CrewAI-simple and justify any added complexity, rather than treating Mem0's formula as the baseline. The 0.85 consolidation-on-save threshold is also the first concrete shipped number for a decision the adopted set leaves open (when a new memory merges with an existing one).

## 8. LangGraph Store: the framework memory substrate (proper inspection)

Sources: LangMem's usage of the store (Section 6), the store's reference surface (operations, `IndexConfig`, TTL behaviour as implemented by its Postgres/Mongo store packages). The store is a namespaced key-value layer separate from the thread-scoped checkpointer (short-term memory): an item is addressed by a namespace tuple (for example `("users", "123", "preferences")`) plus a key, holds an arbitrary JSON value, and the interface is `get` / `search` / `put` / `delete` / `list_namespaces`, in sync and async forms. Semantic search is off unless an index is configured (`dims`, `embed`, and `fields`: only the listed fields of the value are embedded, defaulting to the whole value); per-item overrides exist (`index=False` to skip embedding one item, or a field list to override for one put). Production stores add per-namespace TTL configuration with an optional refresh-on-read, plus a TTL sweeper.
**Verdict: ALREADY-HAVE (substrate) with two ADOPT-IDEA slivers.** The substrate (namespaced JSON store plus optional semantic index) is the file memory's shape with less provenance. The slivers: (1) **per-item index opt-out and field selection** - a stored item can declare itself non-searchable or searchable only on named fields, a useful one-line field for memory files that should be retrievable by path but never surface in semantic search; (2) **TTL refresh-on-read as a named option**, which sharpens pass 2's expiry finding.
**Confidence verdict: CONFIRMS pass 2 correction 17 (Supermemory expiry).** Pass 2 found Supermemory publishes expiry contracts but no algorithm; LangGraph, an unrelated framework, also ships expiry purely as store configuration (a TTL number plus a refresh flag plus a sweeper), with no decay algorithm at the framework level. Two independent sources now support the pass 2 conclusion: expiry in production systems is a contract and a config, and any decay curve would be a local invention, not a copied mechanism.

## 9. AutoGen memory: the minimal interface (proper inspection)

Source paths: `python/packages/autogen-core/src/autogen_core/memory/_base_memory.py` and `_list_memory.py` (both full). The entire framework contract is one abstract class: `MemoryContent` (content as str/bytes/dict/Image, a `mime_type` from a five-value enum, free-form metadata), `MemoryQueryResult` (a list of contents), and five methods, of which the load-bearing one is `update_context(model_context)`: the memory's stated responsibility is to enrich the model context, and implementations decide storage and retrieval entirely. The shipped `ListMemory` keeps an ordered list and its `update_context` renders all contents into a single SystemMessage appended to the context; vector implementations live in the extensions package behind the same interface.
**Verdict: REFERENCE / ALREADY-HAVE, with a warning recorded.** The design lesson is the split itself: `query` (retrieve, caller's problem what to do with it) is separated from `update_context` (the injection policy), which is a clean statement of a boundary the local stack draws implicitly between memory search and synthesis injection. The warning: at interface level AutoGen standardises nothing about scoring, consolidation, provenance, or forgetting, so "framework-compatible memory" claims in this ecosystem mean interface compatibility only. Nothing here competes with the adopted numeric-level discipline; it is evidence of how thin the framework layer is, which retrospectively justifies pass 1's decision to mine memory products and practitioner systems rather than frameworks for mechanisms. (The ChromaDB extension file's path in the current tree did not resolve at the expected location; logged in the ledger rather than chased, since the interface plus ListMemory settle the design question.)
