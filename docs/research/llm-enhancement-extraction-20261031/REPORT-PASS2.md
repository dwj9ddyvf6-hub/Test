No repo code was installed or executed in either pass. No personal information about any person is included.

**Headline: no pass-1 verdict direction was overturned.** Every dive's refined verdict stands in the direction pass 1 gave (adopt-idea, adopt-code, already-have, reference, skip). What pass 2 changed is the *content* of those verdicts: several mechanisms pass 1 described do not exist as described, several exist in much stronger form than pass 1 knew, and two entirely new adoption candidates were found by the expansion dive. **The single deepest find of pass 2** is in Dive 1: Superpowers' **Match the Form to the Failure** table, with its wording micro-testing protocol. It shows that the form of guidance must match the failure type (prohibition plus rationalization table only for discipline failures; positive recipe for wrong-shaped output; structural slot for omissions; observable-predicate conditional for conditional behaviour), and that applying the prohibition form to shape or omission failures measurably backfires, producing more of the unwanted content than a no-guidance control in the corpus's own wording tests. This qualifies pass 1's headline skill-adoption recommendation: rationalization tables adopted without form-matching are a partial, potentially negative adoption.

## 1. What pass 2 changed: corrections and refinements to pass 1 verdicts

Each item is stated plainly. "Correction" means pass 1's statement was wrong or materially incomplete; "refinement" means the direction was right and the buildable content is now different.

### Dive 1: obra/superpowers (PASS2-1)

1. **Correction to Shortlist #6 (rationalization tables).** Pass 1 adopted "TDD-for-skills with rationalization tables" as one discipline. The full corpus shows tables are only one of four matched guidance forms, and the corpus itself warns that prohibition-plus-table applied to shape or omission failures backfires (worse than no guidance in its head-to-head wording tests; a single nuance clause degraded a winning recipe from consistent to noisy; exemption clauses do not scope). Form-matching and micro-testing must be implemented first; tables alone are a partial, potentially negative adoption.
2. **Refinement (verification freshness).** Pass 1 understated the verification gate's freshness unit. The rule is evidence produced **"in this message"**; evidence from a previous message or turn does not satisfy it. The gate also binds language: satisfaction words ("Great!", "Done!") are gated, each claim type has a named sufficient evidence type and a named insufficient surrogate, and agent reports are explicitly insufficient (a VCS diff is the evidence).
3. **Refinement (TDD verification scope).** Pass 1 never surfaced the scope-vs-verification split inside the TDD skill: a task's scope statement bounds the deliverable, not the verification. The project's full test command runs even when the task named one file, and any failure it shows, including one the agent did not cause, goes in the report by name; a red test watched scrolling past and not mentioned is a report falsified by omission.
4. **Refinement (a second false-green defence).** Superpowers' own `writing-good-tests.md` contains a mutation-first false-green defence pass 1 never mentioned: **Name the Break** (before writing a test, name the production change that would make it fail; if you cannot, the test is wrong), plus "exercise the real thing, never mock behaviour." It is parallel to, and composes with, the J1-J6 protocol adopted in round 1 from a different repo.
5. **Correction (brainstorming).** Pass 1 described an earlier, simpler shape ("teases out intent, plays a design back in digestible chunks"). The current 294-line file is substantially more specified: triage first, look before asking, a ~200-word first message ending in exactly one question, one question per message thereafter, anti-goals in the ground, approaches laid out in a message of their own before any write-up, sizing (small design vs full design), a spike valve, and a builder-check subagent whose findings are sorted into exactly three piles (Answered already / Minor / Theirs).
6. **Correction (diagnosing-superpowers).** Pass 1 described a retrospective over four topics (cost, plan adherence, quality evidence, repeated work). The actual system is a forensic protocol: case-file intake, eight report dimensions, a citation-or-discard rule ("Every finding cites `path:line`. No citation, no finding."), a redaction policy with a scrub audit, approval gates before bundling, and an involvement verdict (not indicated / possible / likely) deliberately forbidden from proposing fixes.
7. **Refinement (corpus drift, as a caution).** The corpus violates its own discovery rules in at least two current skill descriptions, and its live-session eval harness (Quorum) lives in an external repo (`prime-radiant-inc/superpowers-evals`, not fetched) with only the static gates safe for public CI. Adopt its tested methods (baseline-first, micro-tests, pressure fixtures) over importing its current texts wholesale; the texts will drift again.

### Dive 2: ECC instincts, eval-harness, AgentShield (PASS2-2)

8. **Correction, the largest in this dive (the injection gap).** Pass 1 stated instincts are "injected in a small ranked budget (about 6, threshold 0.7)" at session start. **No such mechanism exists anywhere in the continuous-learning-v2 directory**: no file reads instincts for injection, no ranking code, no 0.7 injection threshold, no cap of 6. The only thresholds in code are evolve's (workflow 0.7, agent-cluster 0.75) and promotion's (0.8, 2 projects). The "about 6 at 0.7" parameter is retired; any native build must design injection itself. Shortlist #2's build spec changes accordingly.
9. **Correction (confidence mechanics).** Confidence on the session-observation path is capped at 0.85 (3-5 observations = 0.5, 6-10 = 0.7, 11+ = 0.85). The +0.05 / -0.1 / -0.02-per-week adjustment and decay rules exist only as instructions to the observer model; no code adjusts confidence over time and there is no decay job. The 0.9 tier comes only from the repo-analysis source.
10. **Correction (defaults).** The observer is **disabled by default** (`config.json`: `"enabled": false`) and is silently non-functional on native Windows (the spawned observer is killed when the hook's Job Object closes). Pass 1 presented the system as running; as shipped, it does not run until enabled.
11. **Correction (promotion).** The observer agent doc adds a third promotion condition (domain in a global-friendly list) that the CLI does not enforce. The shipped CLI promotes on cross-project ID repetition (2+ projects) plus average confidence at least 0.8 alone. Docs and code disagree; code wins.
12. **Correction (eval-harness gate).** Pass 1's framing implied ECC grades changes by executing them in a harness. **Candidate execution is disabled on every OS** and refuses with `gate.isolation_required`; no trust flag or caller-supplied executor can bypass it. What exists is recording, static inspection, fixture replay, and offline verification. Any claim of containment or promotion evidence from a capsule receipt is explicitly disclaimed by the source itself.
13. **Correction (AgentShield scale).** Pass 1 reported "102 rules" from ECC's README copy. The product repo's own benchmark document and source give **268 rules in 15 modules**. Pass 1's five "categories" are the five *score buckets*, conflated with the rule taxonomy. The effort estimate changes: this is a large taxonomy to mirror selectively, not a 102-item list.
14. **Refinement (AgentShield scoring).** Scoring is per-category first (five buckets starting at 100, floored at 0; overall score is their plain average, so one catastrophic category costs at most 20 points), deductions are weighted by runtime confidence (0.25x template/docs examples to 1.0x active runtime) **except secrets, which always score at full weight**, template-inventory deductions are capped at 10 points per category-file, and recognised defenses are listed in every report but never raise the score.

### Dive 3: Memory internals (PASS2-3)

15. **Refinement (Supermemory profiles have a third axis).** Pass 1 adopted the static/dynamic split. The artifacts add **buckets**: topical partitions (for example preferences, goals, work), independent of the longevity axis, add-only at namespace level (a namespace always keeps every org-level bucket), with bucket descriptions steering the classifier. Also new: the always-on profile is concretely capped at the MCP surface (8 static + 8 dynamic facts), a budget pass 1 never quantified.
16. **Refinement (Supermemory forgetting is four contracts plus a review queue).** Not one expiry mechanism: forget-by-ID (soft-delete, per-ID errors must be checked; HTTP success does not imply every ID changed), semantic forget-matching (mandatory dry-run; bind the real delete to the previewed IDs because re-running the match drifts), decline-as-forget, and time expiry. Plus an inferred-memory review queue entirely missed by pass 1: derived facts carry `isInference` until a human approves (flag cleared), declines (fact forgotten), or undoes; queue rank is by support count (`parentCount`).
17. **Correction (Supermemory extraction is not extractable).** No extraction, edge-classification, or expiry prompt is published anywhere in the tree, and no numeric TTL or decay curve exists in the docs read. Expiry cannot be copied as an algorithm; only its contracts can. The closed-engine caveat is stronger at artifact level than pass 1 stated: the layer producing the benchmark numbers is un-auditable.
18. **Correction (Mem0 temporal ranking).** Pass 1 listed "temporal ranking (current versus past versus upcoming)" as part of Mem0's mechanism. In the open-source build that is **platform-only**: the `timestamp`, `reference_date`, and `decay` parameters raise errors, and `notices.py` is a detection-and-upsell system for temporal-shaped usage. OSS temporal behaviour is a caller-supplied expiration-date filter at search time, nothing more. Strike temporal ranking from the OSS mechanism; a native build must source that design elsewhere.
19. **Correction (Mem0 ships two algorithm generations in one file).** "Mem0 is ADD-only" is true only of the default `add()` path. The same `prompts.py` still ships and exports the legacy ADD / UPDATE / DELETE / NONE memory-manager prompt. Anyone copying "the Mem0 prompt" without naming the constant copies the wrong generation half the time.
20. **Correction (SLM corrections).** Pass 1 described corrections as a simple replace-and-undo (`--replaces <id>`). The current artifact is a **reviewed two-phase lifecycle**: an update creates an immutable successor plus a profile-scoped `proposed` review case; the predecessor stays current until an authenticated reviewer applies the case using its expected version; recall excludes unapplied successors, enforces admission twice (before fusion and after expansion), and **fails closed (abstains) when the lifecycle record cannot be read**. Pass 1's description is superseded.
21. **Refinement (SLM "addition-only" is layered, not a slogan).** Enrichment passes are addition-only; lifecycle zone movement (active / warm / cold / archived, driven by decay models) is autonomous but bounded and protection-gated (maintenance never archives a used memory); corrections are never machine-applied; erasure is a dedicated workflow, never a maintenance side effect. Adopt the layered version.
22. **Correction (Letta is two generations).** Pass 1 described the retired V1 database-block server as "Letta." The current system, letta-code, has converged on git-backed Markdown files (MemFS) with a root index, per-directory indexes, skills as procedural memory, and reflection ("dream") agents: much closer to the reference stack's own architecture than pass 1 conveyed. ALREADY-HAVE stands for the paging idea; the borrowable set is larger than pass 1's "block permissions" (see Section 3, item 7).

### Dive 4: Proactivity internals (PASS2-4)

23. **Correction, the most important in this dive (the pilot has no theta).** Pass 1 framed the awesome-proactive-agents pilot as an implementation of "intervene iff E[benefit] - E[cost] > theta." **The pilot contains no theta variable and never evaluates that inequality.** It implements the *evaluation* half only: a fixed cost-weighted scorer, `score(lambda) = total benefit - lambda * total cost`, swept over lambda in {0.25, 0.5, 1, 2, 4}, which shows post hoc at which interruption price a policy beats silence. The decision half (a fire-time estimator plus a per-context threshold) must be designed; the nearest published gate design is PRISM's (calibrated P(acceptance) against an asymmetric-cost threshold), cited inside the list. Shortlist #1 is adopt-the-scorer plus build-the-gate, not adopt-the-gate.
24. **Correction (ProactiveAgent feedback and gating are thinner than described).** The three-signal feedback policy (accept executes / reject changes approach / ignore throttles, plus no related proposal next turn after an accept) lives in **one sentence of the live prompt**, not in code. The reward-model gate is opt-in by environment variable (`USE_ACTIVERM`); ungated proposals publish by default.
25. **Correction (reward-gate quality is a fine-tuning result).** The reward rubric itself is three operative rules with a binary first-person judgement; all discrimination comes from fine-tuning on human labels via a labelling, rationalisation, and consistency-filter pipeline. A prompt-only rebuild using the published template should expect the repo's own general-model numbers (GPT-4o F1 0.6704, false-alarm slice 0.0), not the fine-tuned F1 0.918.
26. **Correction (benchmark sizes and the false-alarm definition).** Three sizes were conflated: 6,790 events is the corpus; **227 events** is the shipped agent test set; **120 rows** (30 per category, unanimity-preferred) is the reward model's test set on which the headline F1 0.918 is measured. "False-Alarm" in this repo is *defined* as FP/(TP+FP), i.e. exactly 1 - precision; the quoted "GPT-4o false-alarm 51.85%" is 1 - 48.15% precision. The shipped scoring splits also contain no daily-life split, despite the three-category description.
27. **Refinement (internal drift).** The repo is not one coherent spec: the Gym/training schema uses `"Proactive Task"` (with a space, no Operation field) while the live demo uses `"Proactive_Task"` plus `Operation`; the code and data say CR where the README says NR; the retry budget is 3 in the live loop and 15 in training-data generation. A rebuild must fix one spelling, one name, and one budget explicitly.
28. **Refinement (ProactiveEval's rubric lives in its examples).** Stage 1's prompt is four thin rules; the operative rubric is a ~42 KB per-domain few-shot example bank (hand-scored candidate targets with reason paragraphs). Copying the prompt alone will not reproduce the scoring. Stage 2, by contrast, transfers as text: start at 10, deduct 2-4 points per failed criterion across five criteria (goal progression, personalisation, proactive tone, at most 2 sentences / 50 words per message, no metadata leakage). The fair/hard split (157 / 171 of 328 items) is a manufactured refinement gradient (rewrite-to-concrete plus middle-embedded noise), not a found difficulty label.

### Dive 5: Prompting corpus (PASS2-5)

29. **Correction (the Denis rubric has no categories in the artifact).** Pass 1 described self-scoring "each dimension 0-100" as part of the instruction. The Operator block (attempt counting, search after 3 consecutive failures) exists **only in v2** and was silently not carried into v3; pass 1 treated it as current.
31. **Correction (fainir ratios are names, not definitions).** "Memory reuse rate," "percentage of work completed proactively versus reactively," "intervention rate," and "repeat-run stability" each occur only in one metrics list in the 2,949-line prompt block. There is no numerator, denominator, counting rule, or instrumentation instruction anywhere in the file. Adopting the ratios means writing the definitions locally first; pass 1's "tracked metrics" phrasing overstated them.
32. **Refinement (fainir taxonomy is incomplete).** The failure taxonomy has 13 classes but only 8 named repair types; no repair is named for missing permission, context overload, poor model routing, or bad human requirements. Adopting the taxonomy means completing the mapping, not copying it. Pass 2 did extract what pass 1 missed entirely: the concrete loop-guard defaults (pull-based claiming every 30 seconds, ~30-minute hard task timeout, delegation depth ~5, retry once then change strategy or escalate).
33. **Correction (falsegreen protocol is fully in-repo; pass 1's hedge is refuted).** Pass 1 believed "the full protocol lives partly in external docs." The complete protocol, the full **125-code** catalog, the schemas, and the worked examples are all in the repo; the docs site is a rendering. Pass 1 also saw only Mode A (review). Modes B (authoring: generate a test against an elicited independent oracle, then run Mode A on your own output until clean) and C (fix: propose a strengthened test gated by the F7 bidirectional mutation contract) are in the shipped artifact. ADOPT-CODE is **strengthened**, and Shortlist #3 gains two adoption surfaces.
34. **Refinement (DAIR guide evidence grading).** The guide is not flat: two technique pages are placeholders (Directional Stimulus Prompting ends "Full example coming soon!"; graph prompting is one sentence plus "More coming soon!"), the general-tips page carries no citations at all, and magic-phrase results (zero-shot CoT, APE's longer replacement) are 2022-era, model- and benchmark-specific. The strong core (few-shot, chain-of-thought, self-consistency, PAL, ReAct, RAG) has mostly been absorbed into model training or harness architecture. Exactly three things remain live practice: PAL-style offload-to-code, prompt chaining as pipeline decomposition, and APE-style candidate generation scored on examples. REFERENCE stands, refined.

### #3. Rationale memory: decision + rejected alternative + evidence grade (NEW, expansion Section 4.1)

- **What to land:** a rationale entry schema as required fields for the corpora that record decisions (engineering decisions and doctrine lessons; trading-book decisions): stable UUID identity (never a heading), Decision/behaviour, **Rejected alternative(s) with why they lost**, Reason, Type (decision / workaround / incident / constraint / undefined with reason), Status (active / superseded / open / needs-review / pending-confirmation), **Evidence (confirmed / inferred / unknown)**, Source, **Revisit when** (a concrete trigger), See (locator + Id + as-of date), and **Superseded by** (successor Id or "none" with why). Unattended capture writes `pending-confirmation` rather than dropping the finding. - **Why pass 2 raised it:** it is a genuine pass-1 gap. Instincts (#6 below) capture trigger-to-action procedures and the memory discipline (#7) captures fact supersession, but neither captures *why a path was rejected*, which is the knowledge whose absence makes an agent re-propose a dead design. File-native, small-to-medium effort.

### #4. Freshness discipline: timeless, dated, or pointer (NEW, expansion Section 4.2)

- **What to land:** the OKM rule as an authoring law for every maintained memory/knowledge folder: **every stored fact must be timeless, dated, or a pointer; nothing may claim to be current without a stamp.** Legal forms: timeless (no date needed), snapshot (inside a dated note or under a dated heading), pointer ("where truth lives" link plus a last-observed value with an as-of date). The one illegal form: a present-tense claim about a fast fact (volatile within ~7 days: counts, balances, statuses, open items) with no date outside a dated container. Add a FRESH-1-style heuristic check to the nightly pass (error on an unstamped quantitative present-tense claim about a volatile noun outside a dated container), a staleness warning past the freshness window, and the three-answer refresh loop for aged lines: re-observe, convert to pointer, or retire into a dated note. Reimplement the rule; do not import the reference linter (heuristic-tuned to its own vault).
- **Why pass 2 raised it:** pass 1 adopted expiry for temporary facts, but nothing governed unstamped fast facts written as if current, which is the commonest way a memory file silently rots. Cheap (authoring rule plus a heuristic lint), and independently corroborated by the expansion dive's Bilinc find (last-confirmed stamping with a review window, Section 4.7).

### #5. Proactivity, rebuilt correctly: scorer first, gate second, quality rubric third (upgrades Shortlist #1)

- **What to land:** the composed design from Dive 4's synthesis. (a) **Scorer:** the pilot's shape verbatim: log timelines, label MUST (benefit 4) / MAY (2) / MUST-NOT (cost 4) windows with base false-alarm cost 1, credit benefit once per window with MUST-over-MAY precedence, charge cost per fire independently (a violation is charged even on a benefit-earning fire), report fires, MUST recall, violation %, and benefit - lambda * cost at lambda in {0.25, 0.5, 1, 2, 4}; a lane deploys only at the lambda that prices its real interruption cost, and if silence wins at that lambda, silence is the policy. (b) **Gate:** a separate judge pass over (observations, proposed task-or-null) returning a first-person {thought, judgement}; rejection feeds the thought back for a bounded number of *different* retries (pick one budget and fix it), exhaustion is silence, and null is judged by the same gate. Gate quality is built by the labelling pipeline (majority-vote labels, unanimity-preferred test rows, label-conditioned rationalisation, 5-sample consistency filter), with a human-scored holdout the gate never trains on; set expectations at general-model level until that pipeline exists. (c) **Quality rubric:** ProactiveEval's two stages (target correctness first, reference-relative and few-shot calibrated with a locally written per-domain example bank; delivery second, start 10 minus 2-4 per failed criterion). (d) **Feedback:** L0 accept/dismiss/snooze logging with per-context threshold adaptation (maturity level 2) before any learned policy; disabling proactivity is the ultimate negative reward.
- **Why pass 2 raised it:** pass 1's top item survives, but its central object changed: the pilot supplies a scorer, not a gate, and the gate's quality is a data pipeline, not a prompt. Landing pass 1's version as written would have built the wrong thing and expected the wrong accuracy.
