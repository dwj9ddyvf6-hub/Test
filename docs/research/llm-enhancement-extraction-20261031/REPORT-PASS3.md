## 2. The round-3 adoption set

Ten items, ranked by leverage. Every item is a mechanism, a concretisation, or a test shape inside an existing discipline. **No item warrants a thirteenth discipline, and no new discipline-level adoption is proposed.** Compared with round 1 (10 disciplines) and round 2 (12 items, 2 of them new disciplines), this set is deliberately smaller in kind: pass 3 worked the layers around the already-landed material, and what those layers yielded is mostly proof, qualification, and sharpening, with the following genuinely new builds on top.

1. **Scope-creep audit: deterministic diff-vs-intent check** (new; practitioner dive). What to land: a standard-library-only, no-network, read-only script that checks a finished diff against a one-line stated intent and flags unrelated paths, new dependencies, public API renames, config/CI edits, oversized hunks, formatting-only files, and subsystem spread, emitting a keep / split / justify report. Evidence: shipped as working app code in a practitioner collection; it is the mechanical audit of minimum-sufficient-change that no landed discipline currently performs (false-green audits tests; nothing adopted audits scope), and it maps directly onto reviewing delegated work, intent line in the brief, scope report attached to the handback.
2. **User-thrown gate enforcement** (new; fork dive, extends discipline 8). What to land: at plan authoring, tag any task whose brief contains gate language under a strict definition (user gates, agent gates, and the grey zone all tagged; over-tag and let the execution hook filter, rather than interrogating mid-plan); at task close, require evidence in a named form per criterion, and where the verification method itself is unspecified, run a specify-the-HOW protocol (observable outcome, proof mechanism, scope, failure policy, asked at close time) instead of letting the agent invent a method. Evidence: an actively maintained 1,323-star fork built exactly this after observing agents invent expensive verification methods and then walk around them with inline shortcuts. One element explicitly not carried over: that fork's hooks fail open; local gates fail closed.
3. **Operation-level memory scoring, plus a periodic junk-rate audit** (new; research and issues dives, extends disciplines 4, 5, 7, 12). What to land: score the memory pipeline's operations separately, not only end-to-end QA: extraction precision and false-memory rate, update correct / hallucination / omission rates; and run a scheduled junk-rate audit of the stored corpus (hash dedup, near-duplicate clustering, full read of survivors, classify clean / duplicate / hallucinated / malformed / feedback-loop, report the rate). Evidence: a benchmark that scores exactly these three operations exists and is published with a cross-system leaderboard; and the 97.8%-junk production audit supplies both the audit method and the base rate to beat.
4. **Planted-defect probes as the release gate for skill changes, with the vendor eval additions** (upgrade; issues and official dives, disciplines 6 and 7). What to land: before shipping a revised skill, run it against tasks with known planted defects and require detection parity with the prior version; and add to every local eval set a reference solution proving solvability, mandatory balanced should/should-not cases, isolated trials so prior-trial artifacts cannot leak, an explicit "Unknown" exit for model judges, and the rule that a 0% pass-at-many-trials result is treated first as a broken-task signal. Evidence: the source methodology repo ships the planted-defect gate in its own releases with a stated parity result; the additions are the official vendor eval doctrine read in full.
5. **Transactional compaction, with bounds tests and the clear/compact/remember triage** (upgrade; official and issues dives, disciplines 5 and 9). What to land: any compaction that rewrites stored history is generation-checked, serialised against concurrent edits, and restores the prior history on failure; the compaction ladder names tool-result clearing as its first rung, with numeric triage defaults in the vendor shape (clear tool uses at a lower threshold keeping the most recent few, compact at a higher threshold, memory protected from clearing, a save-before-clearing warning); and every summarisation step carries bounds blockers (eviction fraction honoured, structural pairs never split). Evidence: an official SDK session implements the transactional contract; the vendor context guidance supplies the triage; the failure cases that make the bounds tests necessary are reproduced production defects in the paging system's tracker.
6. **Skill-description testing at vendor numbers, with pushy descriptions** (concretisation; official dive, discipline 6). What to land: the description test standard the landing lacked numbers for, a balanced 20-query trigger set (should-trigger plus near-miss should-not) with a 60/40 train/held-out split, selecting on the held-out score, benchmarked with-vs-without the skill in fresh subagents; descriptions written assertively against undertriggering, triggers only, no workflow summary. Evidence: the vendor's own meta-skill ships this loop as an artifact; pass 2 had the method from a community corpus without the description-specific numbers.
7. **Content-addressed fragments for prompt context** (new; practitioner dive). What to land: reusable context pieces (research corpora, teardown bundles, chart packs) addressed by the SHA256 of their content, stored and logged once, attached to many prompts by hash, with an open loader namespace; the hash doubles as the provenance stamp rationale memory wants. Evidence: a mature practitioner CLI ships fragments as its real context mechanism, with loaders for repos, PDFs, threads, and media; passes 1-2 covered memory of facts and procedures, not a hash-addressed context layer.
8. **Confidence-gated adaptive recall depth** (new; practitioner dive, discipline 5/7 numbers). What to land: a cheap first recall whose confidence decides, against two named thresholds (production defaults: return directly above 0.8, explore below 0.5), whether to spend a bounded number (default exactly 1) of deeper exploration rounds, with short queries exempted from analysis; start any native composite scoring from the simple shipped weighting (semantic 0.5 / recency 0.3 with a 30-day half-life / importance 0.2, consolidation-on-save at 0.85 similarity) and justify added complexity, rather than treating the more elaborate published fusion formula as the baseline. Evidence: a major framework's unified memory as shipped code, a second independent composite-scoring implementation converging on the shape with simpler numbers.
9. **Two memory specification additions: episodic exemplars and per-directory self-description** (new; practitioner and research dives, disciplines 7 and 11). What to land: (a) episodic memory retrieved as few-shot exemplars at task time, a curated collection per recurring task class holding situation, approach, and why it worked, the retrieval-side twin of instincts, which store the distilled rule; (b) generated two-level summaries on every memory directory (one-sentence abstract, then overview), read before full content, generalising index discipline from "maintain a root index" to "every directory self-describes at two compression levels"; plus, as a specification sliver from the same research dive, explicit observed-by / knows-about scoping on derived per-person representations. Evidence: a framework conceptual guide states the exemplar mechanism cleanly; a 41k-star context-database system ships the two-level directory contract with unusually complete benchmark reporting; a peer-modelling memory system's deriver supplies the scoping element.
10. **Tracker and gate hygiene pair** (new, small, mechanical; issues dive, disciplines 7 and 8). What to land: (a) a merged-state gate on closure claims, no issue or defect may be closed citing a PR or release without a mechanical check that the PR merged or the release exists; (b) every gate's deny message names the narrowest scoped disable for the specific gate that fired. Evidence: a verified contributor audit of closure claims citing unmerged PRs and a nonexistent release, with the one-line API check supplied in-thread; and a gate that fired on a plain directory listing whose scoped knobs appeared in no documentation, leaving users only the global off-switch.

**Explicitly not promoted to the adoption set** (recorded so the set's boundary is auditable): the experience-memory eval shape from the new LongMemEval-V2 benchmark is adopted as a design template inside item 3's measurement programme and discipline 11's local eval, not as a standalone item; the plan-list-in-JSON hardening, the measured-vs-replayed metric provenance rule, the migration-fixture shape, oracle-staleness as a named false-green class, the firing-example-plus-look-alike rule for audit catalog codes, tool descriptions as eval-tested artifacts, named bounded history-edit operations, numeric effort scaling in delegation prompts, per-item search-index opt-out, and TTL refresh-on-read are all sound, small, and recorded with verdicts in Section 4; each lands as a line inside its discipline when that discipline is next revised, and none needed a ranked place of its own. Padding the ranked set with them would misstate their weight.

## 3. Corrections: errors pass 3 found in passes 1-2 or in the landed reference

1. **Honcho's scope (pass 1 entry corrected, Dive 4).** Pass 1 described Honcho as a hosted-only thin harness. That described only the small Codex satellite repo pass 1 opened. 2. **LoCoMo as evidence (passes 1-2 evidence lines downgraded, Dive 4).** An independent, primary-source-linked audit finds 99 of 1,540 LoCoMo questions (6.4%) have wrong golden answers (scoring ceiling 93.57%), a judge that accepts 62.81% of intentionally wrong vague-but-topical answers in its stress test, an adversarial/abstention fifth of the dataset that no published result evaluates, and a full-context baseline that beats the leading memory system when only the answer prompt changes. LoCoMo rank is retired as supporting evidence for disciplines 4 and 7. No adoption is overturned, because the adopted items are mechanisms read at artifact level, but any landed text that cites a LoCoMo percentage as support should strike it. In the same dive: one source's "#1 on LongMemEval, LoCoMo, and ConvoMem" reduces on inspection to a single published Recall@15 figure for one benchmark with no published QA score, judge, or dataset variant, and is downgraded to unverified vendor marketing; and the Mem0 managed-vs-OSS caveat is confirmed and quantified (managed 94.4 on LongMemEval against 88.6-91.0 for the open-source build under a stronger judge/answerer, extraction-model-dependent, from the vendor's own open harness).
3. **Description hygiene, narrowed (landed discipline 6, Dive 3).** The landed triggers-only rule reads more minimal than the vendor's own guidance supports: descriptions should be assertive ("pushy") against systematic undertriggering, and the one-step-task structural limit was absent from the landed text. Item 6 in Section 2 carries the fix.
4. **Ledger evidence capture (landed discipline 8's source pattern, Dive 1).** The per-plan ledger's automated test-result field in the source implementation records the last log line, not a pass/fail token, and has recorded a duration as an outcome. Anyone copying the source's capture script copies the defect; the landed discipline should state runner-aware capture explicitly.
5. **Letta V1 limits are no longer enforced behaviour (pass 2 sizing note qualified, Dive 1).** The V1 server line's 0.16.7 release deprecates and removes block-limit enforcement; the character limits pass 2 recorded describe the current letta-code generation only and must not be cited as enforced V1 behaviour.
6. **The S-code catalog's proof state (pass 2 adoption qualified, Dive 1).** Pass 2 adopted the false-green catalog at full strength (125 codes, protocol fully in-repo). Pass 3 finds 19 of the 24 semantic codes carry no firing example and no look-alike anywhere in the repo, by the author's own filed issue. The protocol and the structural codes stand; the semantic codes' detection quality is unproven, and the landed discipline's S14/S21 named risks inherit that qualification until each carries both an example and a look-alike.
7. **Mode C's executor (pass 2 adoption surface qualified, Dive 1).** Pass 2 adopted Mode C (fix, gated by F7) as an adoption surface without noting that the shipped executor runs model-generated code with the full ambient environment. The F7 contract stands; the shipped executor must not be run as-is (see discipline 3).

No other pass 1-2 error was found by any dive. In particular, Dive 2 states explicitly that no fork artifact contradicts any of pass 2's artifact corrections (items 8-22 of REPORT-PASS2 Section 1): no fork adds temporal ranking to the open-source memory build, no fork publishes the closed extraction layer, and no fork implements the instinct injection pass 2 proved absent. The adoption set in Section 2 is a transfer judgement against the same reference stack as passes 1 and 2, not a general quality ranking. Discipline numbering follows the landed record, per the note at the top; the two dives that cite the pass-2 adoption-set numbering were re-mapped for this ledger, and that re-mapping is the one editorial transformation this compilation performs on its sources.
