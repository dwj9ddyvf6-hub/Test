## 2. What the repo actually is

A single Claude Code skill (root `SKILL.md`, 32,194 bytes) shipped as a Claude Code plugin (`.claude-plugin/plugin.json` / `marketplace.json`), plus two shell scripts read as text only (`setup.sh`, `scripts/init-wiki.sh`), page templates for Logseq and Obsidian, extensive docs, and an OpenSpec spec tree (348 requirements claimed in the changelog for the plugin spec set). Version 1.7.1 at audit time per CHANGELOG.md.

It implements Andrej Karpathy's "LLM Wiki" gist idea: an LLM maintains a structured, cross-referenced Markdown wiki (the L2), fed by ingest, kept honest by lint, and kept routable by an index-demotion prune. Its original contribution beyond the gist is the two-layer cache architecture and three mechanisms built on it: Hub-Index-Routing, LRU-Demote, and L1-Verification (detailed in section 3).

What it is not: it is not a runtime memory system of its own. L1 is literally Claude Code's own memory directory (`~/.claude/projects/<project>/memory/`) and CLAUDE.md, which the skill reads, classifies, and (with per-item confirmation) edits. It has no session-start hook of its own, and it says so explicitly (see Risks). All intelligence is the hosting LLM following SKILL.md prose; the only executable code is the setup scaffolding.

## 3. Mechanisms extracted (from source)

### 3.1 The L1/L2 split itself (README.md, docs/l1-l2-architecture.md, SKILL.md "L1/L2 Boundary")

- L1: Claude Code memory, about 10 to 20 small files, auto-loaded every session. Contents per the repo: rules and gotchas, identity and preferences, and credentials (see 3.9, rejected).
- L2: the wiki, about 50 to 200 pages in Logseq (outliner, `property:: value`, flat `Wiki___Tech___Page.md` files) or Obsidian (flat Markdown, YAML frontmatter, folder hierarchy `Wiki/Tech/Page.md`). Read only on demand.
- Routing rule, verbatim in substance: "Would the LLM making a mistake without this knowledge be dangerous or embarrassing? Then L1. Merely inconvenient? Then L2." L1 holds operational guardrails that prevent mistakes in the moment; L2 holds contextual knowledge that enriches answers when relevant.
- Boundary migration is expected: L2 to L1 promotion after a lesson is learned the hard way repeatedly (manual decision), L1 to L2 demotion via `prune --l1` (3.6), merge and archive as housekeeping. Lint warns when the same information lives in both layers.
- Size discipline: if L1 grows past about 30 files, audit and move contextual knowledge to L2.

### 3.2 Schema contract (docs/schema-reference.md, templates/obsidian/Schema.md, templates/logseq/Schema.md)

- One Schema page is the contract between user and LLM: 8 default namespaces (Business, Tech, Content, Projects, People, Learning, Reference, Careers), max depth 3, hub page per namespace level.
- 5 page types with required properties: Entity (type, entity-type, created, updated, status, source), Project (status enum, started/completed), Knowledge (domain, confidence high/medium/low/stale), Feedback (severity, verified, applies-to), Hub (namespace).
- Universal rules: ISO 8601 dates, at least one outgoing `[[Wiki/...]]` cross-reference per page, hub lists all children, `updated` holds a date only (change notes go in a collapsed Change log).

### 3.3 Ingest (SKILL.md "Workflow: ingest", openspec/specs/ingest.md)

Five phases: (1) analyze and extract entities, facts, relationships, dates, decisions from a URL (WebFetch), file, or text, classifying each item and running the L1/L2 routing check; (2) scan the wiki (config, Schema, existing target pages) to find affected pages; (3) update pages, targeting 5 to 15 page touches, creating new pages with all required properties, appending new facts, and for superseded state rewriting the block and moving the old wording dated into its collapsed History (nothing deleted), plus maintaining each page's hub routing line and cross-references; (4) quality gate: required properties present, at least one cross-reference, routing line present, no credentials in content; (5) report, then a git commit.

### 3.4 Query: Hub-Index-Routing plus L3 fallback (SKILL.md "Workflow: query")

Two-stage retrieval modeled on a page table. Each hub page carries a `### Index` section of routing lines, one per child: `[[Wiki/NS/Page]] -- <description, max 120 chars> #tags`. Stage 1 reads only candidate namespaces' hub indexes and picks the 3 most relevant pages (max 5) by description. Stage 2 reads only those full pages (max 3 loaded simultaneously) and synthesizes with source attribution, confidence and staleness noted. A full-text grep over all pages is the explicit L3 fallback, used only when routing finds nothing. Optional write-back (create or update a page for a gap or a useful synthesis) requires user confirmation. Git commits are per structural change, not per query.

### 3.5 Access-Log and LRU-Demote prune (SKILL.md, templates Access-Log)

- Every full-page read during query appends one line to an append-only Access-Log page: date, `[[page]]`, `query`, and a `matched:` field (max 60 chars) recording WHY the page was picked: the matched index description/tag, or the grep term on an L3 hit. The log is exempt from orphan/stale/demote rules and is not committed per query.
- `prune` (default 6 months, `--months N`) computes last access per page (never-logged pages use `created` as proxy), exempts hubs, Schema, Dashboard, the Access-Log itself, and active projects, shows candidates before any write, then demotes: adds `archived:: <date>`, moves the routing line verbatim from the hub `### Index` to `### Archive`. Demotion is not deletion and never renames or moves the file (links are by page name; a move would break every backlink). The page stays greppable via L3, and an L3 hit on an archived page offers re-promotion.
- `status` derives a cache profile from the log: hot pages (top 5, 30 days), cold/demote-ready pages, live vs archive index sizes, last prune date, and the most frequent `matched:` reasons per hot page (a page always found by the same grep term signals a weak routing description).

### 3.6 L1-Verification: `prune --l1` (SKILL.md, docs/l1-l2-architecture.md, openspec/specs/l1-l2-routing.md)

The repo's most distinctive mechanism, built on the observation that access frequency cannot detect stale L1 rules because every L1 file loads every session.

- Claim class in L1 frontmatter (two added keys only, other keys untouched, index file excluded): `asserts-current-behavior: true` for a falsifiable claim about a system's current state (path, command, flag, version, port, quirk), `false` for decisions, preferences, identity, rationale (never stale). Behavior claims also carry `verified: <ISO date>`.
- A claim is due when never verified or older than `l1_verify_days` (config, default 90). Lint Rule 12 reports due claims and the unclassified count, never prints L1 file bodies, and never writes to L1, not even with `--fix`.
- `prune --l1` works in confirmed batches of 10: classify unclassified files (proposes true/false with a one-line reason, user confirms or overrides; mixed files are proposed `true` with a suggestion to split; `verified` is never set during classification), then for due rules gather READ-ONLY, LOCAL evidence only (file existence/content, manifests, `--help` / `--version` output; never side-effecting commands, never remote fetches). Verdict is per claim (a rule bundles several): supports / contradicts / inconclusive, with basis type (executed, source, file). External or pricing claims are inconclusive, "not locally verifiable".
- Per rule the user then chooses: re-verify (stamp `verified`; on a contradiction only together with corrected rule text, applied everywhere the claim appears: body, frontmatter description, and index line), demote to L2 (rule becomes a dated history block, `source:: l1-demotion`, on the routed wiki page; L1 file and index line removed only after the wiki write succeeds, with a carry-over summary shown first and references from other L1 files rewritten), delete (carry-over summary shown, references listed), or skip (stays due). Demote/delete first searches other L1 files and the index for references. L1 is not git-tracked, so every L1 write needs per-item confirmation.

### 3.7 Lint: 13 rules (SKILL.md "Workflow: lint", docs/schema-reference.md)

Orphan detection (0 incoming links, hubs excluded); stale detection (updated over 90 days and confidence high); missing required properties; broken references; hub completeness; index drift (active page with no routing line, or routing line with no page); missing index description; archived-in-live-index; credential leak (regex over `token::`, `password::`, `secret::`, `api.key::` and base64-like strings); empty pages; cross-reference minimum (under 1 outgoing link); L1/L2 duplicates; L1 verification due; block bloat (over 600 characters of prose outside History/Change log, or an `updated` value that is more than a date). `--fix` auto-repairs the mechanical subset (backfill routing lines from title plus first block plus tags, clean drift, archive misplacement, downgrade stale confidence, move `updated` notes into the Change log, create stubs for broken links) and never writes to L1.

### 3.8 State + History block format (SKILL.md formats section)

A changing block shows current state on top: one-line headline (status marker, task, due date), queryable properties only, a bold "Next step" as first child, one-line context children, and a collapsed History as last child (Logseq `collapsed:: true`, Obsidian folded `> [!note]-` callout), one dated line per entry, newest first. Updates overwrite headline, properties and next step; superseded wording becomes a history line; interim states that never happened are marked `(superseded)`.

### 3.9 Credentials in L1 (REJECTED)

The repo repeatedly instructs that secrets belong in L1: the README architecture diagram lists "Credentials" as an L1 component and says credentials "must live in L1 because the wiki is typically git-tracked. The L1 memory directory is excluded from git, making it the only safe place for secrets." docs/l1-l2-architecture.md states it as an absolute ("if it is a secret, it goes in L1. Period."), gives a typical L1 layout including `reference_creds.md` ("API tokens and passwords (git-excluded!)"), the FAQ repeats "Credentials must live in L1 (Claude Code memory), never in L2", and SKILL.md's boundary section says "Credentials MUST stay in L1 (wiki is git-tracked!)". There is one softer counter-example: examples/l1-memory-examples.md item 5 stores only a pointer ("All API tokens and secrets are stored in 1Password") rather than values. The load-bearing instruction, however, is the L1 one.

**This tip is REJECTED by the owner, in advance and here on the record.** No secret, key, token or credential is ever written into any memory file, note or vault page in Midna's system, whether or not the containing directory is git-excluded. Secrets live only in the Secure Vault and connector-managed storage, used through the approved credential flow. Git exclusion is not a secret store: memory files are auto-loaded into every session's context, quoted, summarized, backed up and synced, which is exactly the exposure a secret must not have. The separable, sound half of the repo's credential handling is adopted in classification below: scanning the on-demand layer for credential patterns and blocking on a hit (its lint Rule 6 and ingest quality gate) is a leak detector, and that part is endorsed. The destination it prescribes for what it catches is not.

### 3.10 Configuration, setup, status, import (SKILL.md, config.example.yml, scripts read as text)

- `llm-wiki.yml` in the wiki root is read first by every command (missing config aborts with a named message): `tool`, `wiki_path`, `pages_dir`, optional `memory_path` (absent disables all L1 features), `l1_verify_days`, `namespaces`, lint settings (stale days, min cross-refs, credential patterns), ingest settings (target touches 5 to 15, append-only).
- `setup` collects tool, namespaces, optional memory path and git-init consent, then runs `scripts/init-wiki.sh` (creates Schema, Dashboard, hubs, Access-Log, config; skips existing files; optionally `git init` and a commit of only the created files). The standalone `setup.sh` does the same from a terminal and can copy the skill into one project's `.claude/commands/wiki.md`. Neither script was executed in this audit; both were read as text. As read, they contain no network calls, no telemetry and no credential handling; the only URLs are a documentation link printed at the end and the repo URL inside a generated commit message.
- `status`: page counts by namespace and type, oldest/newest updates, lightweight lint, cache profile (3.5), git activity. `import`: inventory existing Markdown, classify, convert to schema format with properties and `[[Wiki/...]]` links, create hubs first, lint, commit.

## 5. Risks

- **Secrets in memory (primary risk, rejected tip)**: the repo's central credential instruction puts API tokens and passwords in auto-loaded memory files, justified only by git exclusion. In any system where memory files are injected into sessions, summarized, backed up and restored (ours are all four), that places secrets on the widest-circulating surface there is. REJECTED by the owner in advance; recorded in 3.9 and in the classification table so no later pass resurrects it as "the llm-wiki way". The related FAQ instruction to "move the reference to L1" after a leak is likewise not adopted; a leaked credential here is rotated and removed, with only a vault pointer, never the value, anywhere in memory.
- **Parallel source of truth**: adopting the wiki as a store (rather than mining its mechanisms) would create a second home for project, people and workflow facts beside ~/MEMORY.md, ~/memory/people and groups, and the midna-book registers, which is exactly the duplication its own L1/L2-duplicate lint exists to fight. The repo also acknowledges the failure mode directly ("Two systems means you need a clear boundary... duplicates mean one copy will eventually go stale"). Any adoption must extend the existing tiers, per the classification above.
- **Destructive L1 operations with no undo**: `prune --l1` can move or delete memory files, and the repo is explicit that L1 is not git-tracked, so there is no rollback. Its mitigations (per-item confirmation, carry-over summary before removal, reference rewrite before deletion, credential rules never demoted) are load-bearing, not decoration. A native version must keep the confirmation gate and should add what the repo lacks: a dated archive copy before any demotion or deletion, since our L1-equivalent (MEMORY.md) is runtime-owned and this program forbids editing it from here in any case.
- **No session-start hook; stale rules act silently between passes**: the repo states plainly that llm-wiki cannot warn when a due L1 rule is about to justify an action, because the host loads L1, not the skill. The due-claim loop only catches staleness at the next lint/prune run. The same limitation would apply to any local reimplementation inside periodic audits; the candidate must not be oversold as a real-time gate.
- **Access-based demotion can bury rare-but-critical pages**: LRU logic demotes what is seldom read. The repo exempts hubs, Schema, Dashboard, the Access-Log and active projects, but a dormant emergency procedure is precisely a cold page that must stay findable. This is why the access-log and prune candidates are bounded and confirmation-gated above, and why they must never touch the runtime-owned memory layers.
- **No phone-home found; one network surface**: as read, the skill, plugin manifests and both shell scripts contain no telemetry, analytics or outbound calls; the README's Privacy section claims the same and the code read supports it. The single network access is ingest fetching a URL the user passes (WebFetch in the host). The un-audited remainder is the host itself (Claude Code and Anthropic processing), which the repo correctly notes is governed by the user's own plan, and which does not transfer to our runtime either way.
- **Concurrent-edit conflicts**: the repo warns that parallel agent sessions writing wiki files can conflict and says to treat the files as a shared resource. Our registers already live under that constraint with job-owned writers; importing a second writer (a wiki maintainer flow) would multiply it. Another reason adoption here means mechanisms inside existing lanes, not a new lane.
- **License and maintenance**: MIT, no barrier to reimplementation. Single author, young repo (created 2026-04-08, last push 2026-10-11, version 1.7.1, 154 stars), Claude Code version-sensitive (README: "Tested with Claude Code 2.1.296", plugin format already broke and was repackaged once at v1.7.0). Bus factor and host-churn risk are real but immaterial if only mechanisms are reimplemented natively, which is this program's rule.
- **Overengineering signal**: 348 specified requirements and 13 lint rules for a personal wiki is a lot of apparatus; the repo itself concedes "the schema feels overengineered at first". Adopting its full surface would import maintenance weight our smaller, already-gated system does not need. The candidate list above is deliberately the minimum sufficient subset.

## 6. Verdict

MehmetGoekce/llm-wiki is the most on-target repo for the assigned question in this sweep's item 7 slot: it is the one that actually designs the split the hint described. L1 (about 10 to 20 auto-loaded memory files: rules, gotchas, identity) versus L2 (50 to 200 wiki pages read on demand), routed by a single test (dangerous or embarrassing if missed goes L1; merely inconvenient goes L2), with the boundary actively maintained by duplicate lint, promotion, and a verification-driven demotion path. Against Midna's existing system the split itself is ALREADY-HAVE in stronger form: four tiers, fixed register schemas, proof-stamped snapshot lines, and a monthly recovery drill where the repo has prose conventions. The genuinely new and useful yield is the L1-honesty package: stamp each auto-loaded system-state claim as `asserts-current-behavior` with a `verified` date, let decisions and preferences carry the never-stale class, surface due claims mechanically, and re-verify them against read-only local evidence with per-claim verdicts, where a contradicted claim can only be re-stamped together with its correction applied everywhere it loads from. A second, weaker package (routing-line discipline for register and research indexes, its three drift checks, and later a bounded access log with demote-not-delete prune) is worth keeping on the candidate list. The repo's credential doctrine is rejected outright: secrets never go in memory files here, full stop; only its credential-leak scanner pattern is endorsed, and we already have a stronger one. Status: PARTIAL, because adoption is out of scope for this program and no candidate is proven until it is reimplemented natively and verified on the final system state.
