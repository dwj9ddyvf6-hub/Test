## BROKER-PENDING-DRAIN-20261026 — pending queue had no caller and was discarded per cycle (CRITICAL, residual of BROKER-BURST-20261026)

- What broke: after the BROKER-BURST in-call retry cure (f69d51b), an
  intent whose submit failed all 3 attempts was appended to the
  Dispatcher’s in-memory `_pending` queue — which had NO caller, and
  desk3/cycle.py builds a fresh Dispatcher every cycle, so the queue
  (and the intent) was discarded at every cycle end. Queued = lost,
  for exactly the intents the burst hit hardest.
- Fix (minimum, at the source — desk3/dispatcher.py + one wiring
  block in desk3/cycle.py):
  1. PendingStore: a durable store under state/ —
     broker_pending.jsonl (append log) + broker_pending.json
     (rewritten snapshot of LIVE entries only), flock-guarded via
     state/broker_pending.lock like the runner’s own files. The
     store is the single source of truth; `_pending` is only its
     same-instance mirror. On final submit failure, process_intent
     persists {intent, sleeve_id, ORIGINAL client_order_id,
     session_date (ET), attempt count, last_error} BEFORE returning
     queued; the slice BP reservation is released (no broker order
     exists; the drain re-runs the BP gate from scratch).
  2. drain_pending() re-runs the SAME process_intent path (slice BP
     gate, A15 reconcile halt, D-GATE, duplicate index — all apply)
     under the ORIGINAL client_order_id, so the broker dedupes and a
     double drain submits/fills once. Fill/submit -> removed +
     journaled `drained`; non-transient reject or gate rejection ->
     removed + journaled `drained_terminal` with the reason;
     transient failure -> stays in the store, attempt count and last
     error updated. retry_pending() now delegates to drain_pending().
  3. Stale-session safety: an entry whose session_date is not today
     (ET) is NEVER submitted — removed at drain time, journaled
     `expired_unsent`, zero broker calls. A reconcile-halted sleeve’s
     entry is not submitted while halted: it stays pending, journaled
     `pending_drain_deferred`, and drains when the halt lifts in the
     same session.
  4. Wiring: desk3/cycle.py calls disp.drain_pending() at the START
     of dispatch (after the A15 halt set is applied to the
     Dispatcher, before this cycle’s new intents), naming the result
     in the roll (pending_drained / pending_drain / pending_drain_error).
  5. Bounds: DRAIN_CAP=20 entries per cycle — one entry costs at
     most 3 bounded submits + 1 read-back (~1s worst-case retry
     backoff), so drain adds ≤~20s inside a 60s cycle and can never
     starve new intents; leftovers stay queued (20/cycle still
     clears 1200/hour). The stale sweep is not charged to the cap
     (no broker calls). Store files hold only live entries: every
     terminal outcome removes its entry and compacts both files, so
     a pathological day cannot grow the store without bound
     (MAX_PENDING_ENTRIES=1000 documents the live-backlog scale).
  Idempotence is preserved end to end: original client_order_id on
  every re-submit, the dispatcher’s _seen index, and broker-side
  client-order-id dedup.
- Blockers: tests/test_broker_pending_drain_20261026_blockers.py
  (8 tests, gate-wired by the test_*_blockers.py discover pattern):
  (a) an intent failing all retries is persisted (full record,
  original coid, attempts=3, last_error) — pre-cure it was discarded;
  (b) a FRESH Dispatcher drains a persisted intent under the SAME
  client_order_id to filled, store emptied, `drained` journaled;
  (c) a stale-session entry is expired_unsent with broker submit
  count 0; (d) a reconcile-halted sleeve’s pending intent is not
  submitted while halted (stays pending) and fills after the halt
  lifts; (e) draining twice submits once and empties the store;
  (f) a non-transient 422 on drain is drained_terminal and removed;
  (g) DRAIN_CAP bounds per-cycle drain work with the remainder
  staying queued; saty_sol sha256 pin.
- Fail direction (proven 2026-10-26): with desk3/dispatcher.py and
  desk3/cycle.py temporarily reverted to f69d51b, the blocker file
  reports FAILED (7 errors of 8 — only the saty_sol rails pin passes,

## DRAIN-CLASS-20261026 — pending drain discarded broker_unavailable-class intents as terminal (CRITICAL, live session)

- Severity: CRITICAL — silent loss of pending intents during the
  live 2026-10-26 session: 40 pending intents were discarded by the
  drain with reason 'FetchError:HTTP 403'. They are NOT recoverable
  from the store (the drain removed them); they are recorded here by
  count and reason only — no recovery is fabricated, and their
  sleeves re-derive signals per cycle.
- What broke: desk3/dispatcher.py classified a submit failure as
  transient only for status None / 429 / >=500. An HTTP 403 therefore
  returned queued with transient=False, and drain_pending() treated
  `queued + not transient` as drained_terminal and REMOVED the entry.
  A transport/HTTP failure is never a terminal broker answer: the
  403 class (Alpaca 40310000, see ORDER-403-20261026 below) is an
  account-state answer that can clear, not a rejection of the intent.
- Fix (minimum, at the source): one classifier,
  _broker_unavailable_class(status) in desk3/dispatcher.py — status
  None (network), 403, 429, or >=500 — now serves BOTH places the
  dispatcher distinguishes the classes (the bounded in-call retry in
  process_intent and the drain). At drain time an unavailable-class
  outcome leaves the entry IN the store and is journaled
  `drained_deferred` with the error (result status drained_deferred).
  Only outcomes outside the class may drain_terminal: a genuine
  terminal broker rejection (e.g. 422 validation) or a gate
  rejection (`rejected`) — both unchanged.
- Blockers: tests/test_drain_class_20261026_blockers.py (6 tests,
  gate-wired by the test_*_blockers.py discover pattern): 403 / 429 /
  503 / network-error at drain -> entry stays, drained_deferred
  journaled with the error, no drained_terminal; 422 at drain ->
  drained_terminal and removed (never retried in-call); saty_sol
  sha256 pin.
- Fail direction (proven 2026-10-26): the new blocker file run
  against the pre-cure (fd57f0d) dispatcher FAILED 4 of 6 (403
  misclassified transient=False; every unavailable-class drain
  returned plain queued with no drained_deferred journal and, for
  403, removed the entry as terminal) while the 422-terminal and
  saty_sol pin rows passed, as designed; post-cure 6/6 OK and the
  scoped suites (drain-class + broker-pending-drain + remainders +
  scale-fault) pass 28/28.
- Rails held: paper only; no strategy/sizing/stops/threshold
  changes; no global pacing (R-5 — the in-call retry stays bounded
  at 3 attempts at the intent's own dispatch moment); Tensor engine
  untouched; sleeves/saty_sol.py sha256 36e306c6... byte-identical

## GATE-MASK-20261026 — regression gate exit code masked by `| tail -5` (CRITICAL, integrity)

- Severity: CRITICAL — the gate could not fail. Every "gate GREEN"
  verdict ever produced by run_regression_blockers.sh was, as far as
  the exit code was concerned, unproven: a caller checking $? always
  saw success.
- What broke: the script runs under `#!/bin/sh` with `set -e` and
  ended with `python3 -m unittest discover ... 2>&1 | tail -5`.
  POSIX sh has no pipefail; a pipeline's exit status is its LAST
  command's — tail's, which is 0 whenever tail runs. unittest's
  failure code was discarded by construction.
- Fix (at the source, run_regression_blockers.sh): unittest now
  redirects to a log inside GATE_TMP; its exit code is captured
  (`|| rc=$?`, immune to `set -e`) and re-raised via `exit "$rc"`.
  The human-readable `tail -5` of the log is still printed.
- Proof, BOTH directions, on the final script:
  (a) healthy tree: full gate — Ran 1249 tests, OK, exit code 0.
  (b) scratch copy with one blocker deliberately broken (an assertion
  in tests/test_gate_mask_20261026_blockers.py flipped to expect
  "DELIBERATE_BREAK"): the broken test fails (verified standalone:
  AssertionError 'DELIBERATE_BREAK' not found in the inner gate's
  FAILED tail) and the gate exits 1.
- Blocker: tests/test_gate_mask_20261026_blockers.py (gate-wired) —
