- Severity: critical (the Tensor daily20 rows store, sole feed for

- Found live by the 2026-11-02 v3-daily20-store-rebuild cron. The
  prescribed rebuild (build_id parity-20261102, launched 22:47Z)

- Root cause: pool workers raise tensor_engine.TensorEngineError on
  a bad tape (on 2026-11-02 ABCB's live Yahoo tape trips "Native
  OHLCV has invalid prices, volume or candle envelope"; in October
  ABCB built fine). ProcessPoolExecutor's parent must UNPICKLE each
  worker exception off the result pipe, which requires the raising
  module to be importable in the parent. daily20_producer._handoff()
  inserts HANDOFF_BACKEND into sys.path only in the process that
  calls it; the prescribed launch (python3 -m desk3.daily20_producer)
  never called it in the parent, so tensor_engine was unimportable
  there. The first engine error (ABCB, ~2s into the build) killed
  the executor's result handling, every pending future was reported
  BrokenProcessPool, the retry pool died the same way on the same
  symbol, and build_store converted the wreckage into
  excluded-by-name rows and rewrote the manifest from them.
  Proof both directions, isolated from the live store: the same 12
  symbols through _build_one under a hand-rolled pool all complete
  (the wrapper caught the exception inside the worker); submitting
  _build_one directly breaks every future at ~2.1s; inserting
  HANDOFF_BACKEND into the parent's sys.path before the pool makes
  ABCB raise cleanly as TensorEngineError and the pool survives.
  October's build escaped only because its parent process happened
  to have the engine importable (its UA/WLY engine errors crossed
  as named errors, per its ledger).
- Fix (source, minimum sufficient): build_store() in
  desk3/daily20_producer.py now calls _handoff() first, priming the
  parent-side engine import before any pool work, under every launch
  route. No strategy, sizing, threshold, or Tensor engine change;
  engine pins untouched.
