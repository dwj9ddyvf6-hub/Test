## HOOKS-LEDGER-STREAM-20261109: fire_hooks materialised the estate ledger twice and the daily runner was OOM-killed in the hooks stage (CURED)

- Severity: run-fatal (the 2026-11-09 daily run compiled
  and published its state at 23:26:25Z, regime Fearful,
  composite percentile 30.1, then was killed, exit 137,
  inside fire_hooks; hooks-day-one.json stayed at its
  2026-11-06 write and the hooks evaluation for the night
  never completed or logged).
- File: pipeline.py, fire_hooks.
- Root cause, measured: fire_hooks called Ledger.rows()
  for its before count (a full parse of
  forecast/ledger.jsonl: 622 MB, 296k rows that evening),
  appended (which changed the file), then called rows()
  again for the after count, re-parsing the entire ledger
  into a second parsed copy while the first was still held
  by the ledger's cache; verify_chain() and the backdated
  scan worked over the materialised rows as well. Measured
  in isolation on the same ledger that night: one rows()
  parse of 309,781 rows peaks at 2,252 MB RSS, so the
  stage's two coexisting copies alone needed about 4.5 GB
  on top of the runner's retained collector and compile
  state, on a cell with a 6 GB shared limit. The
  muse-desk-v3 daily20 rebuild (3 workers, running since
  17:46 ET) added real contention that evening, but the
  stage was intrinsically unsafe at this ledger size; the
  contention hypothesis alone does not explain the kill.
- Fix: fire_hooks never materialises the ledger. One
  streaming pass over Ledger.iter_rows() computes the
  before count, the backdated scan and the F1 dedupe scan
  (the same key append_forecast computes, via
  Ledger._forecast_body); the append consumes the ledger's
  own streaming append state (append_stream_state plus
  _append_streaming, with the append state refreshed when
  a concurrent writer lands first), because
  append_forecast_streaming's batch convention
  (horizon_open == issued_ts) does not fit F1, whose
  horizon is the next AAII print date; the after count is
  a second streaming pass and chain validity is
  verify_chain_streaming(). Every output field and the
  dedupe semantics are unchanged (proven: a second
  consecutive call returns the same row_id with
  created=False and appends nothing).
- Regression blocker:
  tests/test_fire_hooks_streaming_20261109.py (a Ledger
  whose rows() raises AssertionError must still see the
  stage complete: F1 created, counts 3 to 4, chain valid,
  one backdated row counted; fails on the old code, where
  the stage dies on the first rows() call).
- Proof: a complete run_daily.py run on the cured code
  finished the night of 2026-11-09/10: state-latest.json,
  STATE.md, feed.json and the midna-book SENTIMENT-STATE
  files written 2026-11-10T01:11Z, hooks-day-one.json
  written 01:13Z carrying ledger_rows_before 325607,
  ledger_rows_after 325607, chain_valid true,
  backdated_psychology_rows 0 and no error key. (The
  detached wrapper's exit-code line was lost when the
  wrapper was reaped; completion is proven by the final
  artifacts.) The cured stage alone, re-run against the
  real 325,607-row ledger in a measured subprocess, peaks
  at 19.8 MB RSS and exits 0. Zero hooks fired because
  none were due: F1's input series (aaii_weekly) is a
  header-only absence note under its stated limit (see
  external blockers below), F2's trigger was not met, F3
  is gated out by design, F4 found no signature. The
  ledger holds zero psychology_engine rows in its entire
  history, so nothing was issuable that night either.
- Bounded loss, named: the 2026-11-09 hooks evaluation
  never completed or logged (the stage was killed), and

## BELIEF-LEGACY-KEY-20261109: collect_belief lost every Polymarket and Kalshi snapshot to a KeyError on the legacy rows (CURED)

- Severity: source-fatal nightly (polymarket_daily and
  kalshi_daily logged FAILED 'key' on 2026-11-04, 05, 06
  and 09 while their fetches succeeded; the saved raw
  responses under live/raw/collect_belief/ are complete).
- File: pipeline.py, collect_belief (both venue merges).
- Root cause: the stored series carry columns
  [date, venue, event, probability, volume] with no "key"
  column and one legacy row each. The merge keyed its dict
  by r.get("key") or date|event but kept the original
  keyless row dicts as the values; write_series computes
  its span from the first column, "key", so the write
  raised KeyError('key') and the whole night's snapshot
  was lost after the merge had already been built.
- Fix: the merge writes the key back into every stored
  row (merged[k] = {**r, "key": k}), so the stored series
  gains the key column the writer requires and no legacy
  row can fail the write again.
- Regression blocker:
  tests/test_belief_legacy_key_20261109.py (seeds keyless
  legacy CSVs, patches the fetches with the saved payload
  shapes; asserts both venues store the new snapshot and
  preserve the legacy row under its synthesised key;
  fails on the old code with KeyError 'key').
- Proof: live collect_belief() on 2026-11-10 stored 20
  Polymarket rows and 10 Kalshi rows for the day, legacy
  2026-10-30 rows preserved under synthesised keys.

  to the legacy key.

## BAKER-WURGLER-XLSX-20261109 / BAKER-WURGLER-DATA-SHEET-20261109: dead fallback endpoint, then the wrong sheet and headers of the successor workbook (CURED)

- Severity: source-fatal (baker_wurgler_monthly failed
  every run; after the endpoint cure it logged ok with
  zero rows, which is worse: a silent absence).
- File: pipeline.py, bf_baker_wurgler.
- Root cause, in three layers, each proven separately:
  (1) the discovery pages refuse this client (403), so
  the hardcoded fallback decides, and it named
  SENTIMENT.xls, a genuine 404 (the author removed it);
  SENTIMENT.xlsx in the same directory answers 200.
  (2) The parser read wb.sheetnames[0], which in the
  published workbook is a README sheet; the series lives
  on a DATA sheet, so the parse stored zero rows.
  (3) The value lookups named SENTIM/SENTIMo; the DATA
  header is yearmo/SENT/SENT_ORTH, and the level fallback
  list(vals.values())[0] stored the indpro column as
  sentiment for the pre-1965 rows whose SENT is empty
  (caught on the first live landing: 816 rows including
  about 90 macro values mislabelled as sentiment).
- Fix: fallback URL is SENTIMENT.xlsx; the parser selects
  the sheet whose header names a yearmo column; level and
  orthogonalised values are read case-insensitively under
  the published and legacy names; the first-column
  fallback is removed, so a row counts only when the
  sentiment column itself is populated.
- Regression blockers:
  tests/test_baker_wurgler_xlsx_fallback_20261109.py (the
  legacy-shape fallback test, plus a published-shape test:
  README first sheet, DATA headed yearmo/SENT/SENT_ORTH,
  a SENT-empty but indpro-populated 1958 row that must
  not be stored; the published-shape test fails on the
  pre-cure parser).
- Proof: live collector run stored 726 rows,
  1965-07-01 to 2025-12-01, first value -1.97769033908844
  matching the workbook exactly, zero pre-1965 rows.
